## A filename names the ink, not the background

`-dark` is the **black** wordmark, which is used **on light** backgrounds.
`-light` is the **white** one. The kit's own `README.txt` says so, and the
folder pair `logo/dark` and `logo/light` follows the same rule.

It reads backwards the first time and it has been got backwards before: until
AGL-3216 every PNG and PDF in the org library carried the inverted suffix. The
artwork served was always right, so nothing looked broken on the page — but the
download route builds `content-disposition` from `fileName`, so the black
lockup arrived on a journalist's disk called `…-light.pdf`, which is precisely
the file you would reach for to put type on a dark background.

The kit is the arbiter, and it settles this cheaply: its files are byte-unique,
so sha256-matching a DAM asset against the extracted ZIP names it exactly.

## Exporting a mockup for the website

This has been got wrong more than once, and always the same three ways: a drop
shadow baked into the pixels, white padding around the artwork, and opaque
corners. The website draws its own shadow and its own radius — the shared
`Product detail hero` component sets `borderRadius: 16px` and `boxShadow: 24`
on the `<img>` itself — so a shadow in the file is a second shadow, and padding
in the file is a mockup that no longer touches its own card.

Two Figma behaviors cause all three, and neither is obvious:

- **An export's bounds include effects.** A drop shadow with `radius: 64,
  spread: -12, offset: (0, 32)` pushes the exported box out on every side, so
  the "screenshot" arrives ringed by shadow and smaller than the frame it came
  from. Strip effects and the bounds equal the frame.
- **An export is composited onto the page background.** Figma's default canvas
  grey is `#F5F5F5`, and it fills the corners a `cornerRadius` would otherwise
  leave transparent — which is how a file ends up with square opaque corners
  that the CSS radius then has to clip twice.

So, to export:

1. Clone the frame and strip `effects` from the clone **and every descendant**.
2. Move the clone to a page whose background is a solid paint at `opacity: 0`.
   Page backgrounds must be a single solid paint — `backgrounds = []` throws.
3. Export at 2x. Delete the page when the bytes are downloaded; the masters
   keep their shadows, because the Figma design is not wrong, only the export.

Check the result before uploading: the four corner pixels must read `alpha 0`,
the mid-edge pixels must be opaque, and the size must be exactly 2x the frame.
Press screenshots and product mockups are **1840x1160** — the intrinsic pair
the hero component declares — so a frame is 920x580 before export.

## Minting a lockup PDF

Every lockup PDF's MediaBox is the SVG viewBox **x10** in points: `plugins`
148x24 becomes 1480x240, `crm` 118.806x24 becomes 1188.06x240. Nothing enforces
that; it is simply what all of them do, and a new one that disagrees is the odd
file in a set people diff.

Reproduce it from the component rather than from the SVG on disk: create an
instance, `rescale(10)`, export as PDF. `Producer` then reads `Figma` like the
rest of the kit. ⛔ Do not rasterize these SVGs with ImageMagick to check them —
their root `style` carries `stroke-linejoin`/`stroke-miterlimit` and a
`magick` render outlines every path, making the artwork look far heavier than
it is. Render with headless Chrome, or read the PDF.

## Rebuilding the kit ZIP

The ZIP is the canonical set and the press page links it directly, so it has to
stay ahead of the individual downloads rather than behind them. Extract, add,
rewrite `README.txt` — including its version line and the paragraph listing
which products ship which formats, which has promised a format it lacked before
— rezip, then replace `v1Sn-yqHsN` **in place** so the URL survives.

Verify by fetching the served bytes back and diffing the manifest against the
old one. The expected diff is additions only; anything that disappears is a
file someone still links.

## Replacing a DAM asset

⛔ **Never upload a second copy of an asset that already exists — replace it.**
A new upload mints a new id and a new URL, so the old one goes on serving its
old bytes to everything that already links it, which is the exact failure
replace-in-place was built to prevent. It happened once, to the logo kit: a
10 Aug ZIP sat beside the live one under the same filename until AGL-3216,
twenty-two files behind and linked by nothing.

The sweep that finds this groups the library by `contentSha256` — the same
bytes under two ids is an upload that should have been a replace — and by
`fileName`, since two assets with one name are indistinguishable in a picker.

Replace-in-place keeps the id, `cdnPath`, `storagePath` and `url`, and drops
the derived artifacts so nothing stale survives (AGL-2732). **An image must go
through the console** — it has `variants` (320/640/1280/1920 WebP) that only
the upload route regenerates, and a service-account write would leave the old
renditions serving under the new id. A PDF or a ZIP has no variants, so either
route is sound for those.

After replacing an image, check every declared `intrinsicWidth`/`intrinsicHeight`
that points at it. `srcset` picks a width from the declared pair, so a pair left
describing the previous file upscales the new one.

And read an asset before you replace it only when you have to: a `?download=1`
fetch **warms the edge with the pre-replacement bytes**, and that entry can
outlive its own `max-age=60` by twenty minutes or more. The plain URL will serve
the new file while the download link still serves the old one.

## Deleting one

Prove it is unreferenced first, and prove the proof discriminates by running the
same scan against an asset you know is used. Scan every host's screens — **all
versions, not just the published one** — plus components, layouts, emails and
the host documents. The console's own *Find where this is used* says out loud
that it checks neither unpublished versions nor order history. Keep the bytes.

## The guidelines deck

`aglyn-brand-guidelines.pdf` is not authored as a PDF: it is the twelve
`Brand Guidelines · NN · …` frames, exported and merged, as the note on that
Figma page says. Slide 07 carries one row per product lockup and slide 10 names
the products in prose, so a new product touches both. Check slide 07 by
**rendering** it — the lockups are artwork, so a text-layer search finds
nothing and will tell you a product is missing when it is there.
